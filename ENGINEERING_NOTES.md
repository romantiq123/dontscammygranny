## 1. Нативный слой (llama.cpp + JNI)

Мост: `app/src/main/cpp/llama_bridge.cpp`. Вендоренный llama.cpp — submodule
`app/src/main/cpp/llama.cpp`, коммит `76f46ad2` (тег `gguf-v0.19.0-1029`).
**llama.cpp не держит стабильный C API между релизами** — при обновлении submodule
сверяться с `include/llama.h` этого коммита, прежде чем считать ошибку сборки багом логики.

### 1.1 `-O3` не доезжал до ggml → `llama_decode` 113 секунд

**Симптом.** Инференс «зависал»: декод промпта из 137 токенов занимал ~113 с (ожидалось <1 с),
процесс успевала прибить система. Пересборка «не помогала», размер APK не менялся.

**Причина.** Для debug-варианта AGP передаёт `CMAKE_BUILD_TYPE=Debug`, и NDK-дефолт
`CMAKE_C_FLAGS_DEBUG` = `-g` (фактически `-O0`). Попытка переопределить через
`set(CMAKE_C_FLAGS_DEBUG "-O3" ... FORCE)` **не работала**: переменная попадала в
`CMakeCache.txt`, но **не в команды компиляции таргетов ggml** — проверено по
`app/.cxx/.../build.ninja`, где `-O3` не встречался ни в одном из ~198 файлов, зато
`-g` встречался 198 раз. CI-сборка была быстрой, потому что CI собирает **Release**,
где ggml сам ставит `-O3` (отсюда же и разница размеров APK: 24 МБ debug vs 17 МБ CI).

**Фикс.** В `app/src/main/cpp/CMakeLists.txt` **до** `add_subdirectory(llama.cpp)`:
```cmake
add_compile_options(-O3)
add_compile_definitions(NDEBUG)
```
Это свойство `COMPILE_OPTIONS` директории — наследуется всеми таргетами ggml/llama и
гарантированно попадает в команду компиляции (в отличие от `CMAKE_*_FLAGS_DEBUG`).

**Как проверить.** Перегенерировать CMake той же командой, что использует AGP (её точный
вид лежит в `app/.cxx/<variant>/<hash>/<abi>/metadata_generation_command.txt`), затем
поискать `-O3` в `build.ninja`. После фикса: **193 вхождения**, включая `ggml-cpu.c`.

> ⚠️ **Чтобы применилось — нужен ЧИСТЫЙ пересбор нативки**, см. [5.1](#51-чистый-пересбор-нативки-обязателен).

### 1.2 SIGSEGV на первом же токене — двойной `accept`

**Симптом.** `nativeLoad` возвращал валидный handle, генерация начиналась, но процесс
умирал сразу после первого токена (в логе: `iter 0 <- sampled id=5212` → приложение
перезапускается). `FileLog` ничего не успевал записать — нативный краш.

**Причина.** Цикл генерации вызывал `llama_sampler_sample(...)`, **а следом ещё и**
`llama_sampler_accept(...)`. Но в этом коммите `llama_sampler_sample` **сам делает accept
внутри** (см. `llama.cpp/src/llama-sampler.cpp`, конец функции). Двойной accept продвигал
состояние grammar-сэмплера (PDA/стек) дважды на один токен → порча состояния → segfault.

**Фикс.** Убран лишний `llama_sampler_accept` из цикла в `llama_bridge.cpp`.

**Как проверить.** Лог идёт дальше первого токена: `sampled id=…` → `piece n=…` → … →
`EOG, стоп` → `<- nativeInfer вернул …`, приложение не перезапускается.

### 1.3 KV-кэш не чистился между вызовами → падал 2-й и 3-й инференс

**Симптом.** Первое сообщение обрабатывалось нормально, второе падало на `iter 0`
(`llama_decode(next) вернул != 0`), третье — сразу на декоде промпта.

**Причина.** `llama_context` и сэмплер переиспользуются между вызовами `nativeInfer`, а
токены **накапливались** в KV-кэше от сообщения к сообщению → переполнение `n_ctx` →
`llama_decode` возвращал ошибку. Плюс росла латентность (attention по всё большему
контексту). Grammar-сэмплер тоже копил состояние прошлого разбора.

**Фикс.** В начале каждого `nativeInfer`:
```cpp
llama_memory_clear(llama_get_memory(handle->ctx), true);
llama_sampler_reset(handle->sampler);
```
> В этом коммите KV чистится через **новый memory-API**, а не `llama_kv_cache_clear`.

**Как проверить.** Послать 3+ сообщения подряд — все должны отработать одинаково; в логе
на каждом инференсе строка `KV-кэш очищен, сэмплер сброшен`.

### 1.4 GBNF: многострочное правило молча не парсится → nullptr → segfault

**Симптом.** `nativeLoad` возвращал handle, первый `nativeInfer` ронял процесс.

**Причина.** Парсер GBNF в llama.cpp **заканчивает правило на первом `\n`**, если оно не
обёрнуто в круглые скобки. Многострочные последовательности/альтернативы без скобок не
парсились → `llama_sampler_init_grammar` возвращал `nullptr` → `nullptr` клался в цепочку
сэмплеров без проверки → первый `llama_sampler_sample` дёргал `apply()` у null.

**Фикс (три части).**
1. `verdict.gbnf` переписан по канону `json.gbnf`: `root` — **одной строкой**, enum-списки
   в скобках `( ... )`.
2. `llama_bridge.cpp`: **null-check** результата `llama_sampler_init_grammar` — если
   грамматика не распарсилась, работаем без неё (greedy) и явно пишем это в лог, а не падаем.
3. `.gitattributes`: `*.gbnf text eol=lf` — см. [1.6](#16-crlf-ломает-грамматику).

**Как проверить.** В логе при загрузке: `nativeLoad: грамматика распарсилась ОК, сэмплер с GBNF`.
Если увидишь `ГРАММАТИКА НЕ РАСПАРСИЛАСЬ` — вывод не будет соответствовать схеме, но процесс жив.

### 1.5 GBNF: `ws*` в начале `root` → модель залипает на пробелах

**Симптом.** Инференс отрабатывал целиком, но выдавал 64 токена подряд с одним и тем же
id (whitespace) — на выходе 67 пробелов вместо JSON → `JSONException: End of input`.

**Причина.** `root` начинался с `ws ::= [ \t\n]*` — неограниченный whitespace. Слабая
0.5B-модель на нём залипает: greedy бесконечно выбирает пробельный токен, а `ws*` его
**всегда пропускает**, поэтому до `{` дело не доходит.

**Фикс.** Правила `ws` убраны из грамматики вовсе → форсится **компактный** JSON
`{"level":...}`: на каждой структурной позиции валиден ровно один символ, модель обязана
его выдать; свобода выбора остаётся только на enum-значениях (это и есть классификация).

> Побочно: `validate_gbnf.py` больше не считает валидным пример с пробелами внутри JSON —
> это ожидаемо, модель такого и не сгенерирует.

### 1.6 CRLF ломает грамматику

**Причина.** Git на Windows с `autocrlf` подсовывал `verdict.gbnf` с `\r\n`, что ломало
парсер GBNF (см. 1.4).

**Фикс (два уровня).** `.gitattributes` → `*.gbnf text eol=lf`; плюс в `llama_bridge.cpp`
на всякий случай вырезаются `\r` из текста грамматики перед передачей в парсер.

### 1.7 Копия грамматики в assets

`app/src/main/assets/verdict.gbnf` — **копия** корневого `verdict.gbnf`. Приложение грузит
именно ту, что в `assets`. При правке схемы синхронизировать **обе** (плюс
`verdict_schema.json` — источник истины, ADR-004).

## 2. LLM: промпт и модель

### 2.1 ChatML — главный разблокировщик качества

**Симптом.** Модель возвращала валидный JSON, но **побайтно одинаковый** на разных входах:
`{"level":"none","confidence":"0.0","category":"none","reason_code":"no_signal"}`. Т.е.
классификация игнорировала содержание сообщения.

**Причина.** Промпт подавался **сырым текстом**. Instruct-модели Qwen обучены на формате
**ChatML** (`<|im_start|>role … <|im_end|>`) — без него модель не в режиме «следуй
инструкции» и greedy схлопывается в дефолтный ответ.

**Фикс.** `LlmPromptBuilder` собирает ChatML: `system` (роль + правило + глоссарий
признаков) → две **настоящие** пары `user`/`assistant` few-shot (скам→danger,
безобидное→none) → реальный запрос → `<|im_start|>assistant`.

Ключевые детали, которые делают это рабочим:
- токенизатор моста вызывается с `parse_special=true`, поэтому маркеры ChatML — **реальные
  управляющие токены**, а не текст;
- закрывающий `<|im_end|>` ассистента — это **EOG** (id `151645` у Qwen), поэтому цикл
  генерации останавливается сам;
- в системном промпте явное правило: «regex уже нашёл категорию — **по умолчанию подтверди**;
  `none` только если текст явно безобиден» (мелкая модель иначе тяготеет к `none`).

**Подтверждено на устройстве.** Вход «Перейдите по ссылке http://kaspi-secure.xyz и
подтвердите данные карты» → `{"level":"warn","confidence":"0.9","category":"phishing_link",
"reason_code":"suspicious_link_domain"}` — привязано к содержанию. Aggregator поднял
confidence 0.4 → 0.9.

> **Вывод для будущих экспериментов:** прежде чем менять модель на более крупную ради
> качества, убедись, что она получает промпт **в своём родном чат-формате**. Здесь это
> дало больший эффект, чем смена поколения модели.

### 2.2 Бюджет контекста: промпт vs `N_CTX`

ChatML с few-shot стоит контекста: фиксированная часть промпта ≈ **250–310 токенов**.
При `N_CTX=512` на само сообщение оставалось ~120 токенов — длинное SMS переполняло
контекст, `llama_decode` возвращал ошибку, и LLM молча терялся (откат на regex — graceful,
но слой не работал).

**Текущие значения** (`LlamaCppExecutor`): `N_CTX=1024`, `MAX_TOKENS=64`,
`MAX_INPUT_CHARS=1200`, `N_THREADS=4`. Для 0.5B это ~25 МБ KV-кэша.

> При переходе на модель крупнее — пересчитать: KV-кэш растёт, а `MAX_INPUT_CHARS`
> должен оставаться заведомо меньше, чем `N_CTX` минус промпт минус генерация.

### 2.3 Смена модели — правка двух строк

Целостность докачки проверяется по **`Content-Length` сервера**, а не по захардкоженному
размеру (константа `EXPECTED_MODEL_BYTES` удалена). Поэтому смена кандидата ADR-003 — это
правка только `MODEL_FILENAME` и `MODEL_URL` в `LlamaCppExecutor` (+ промпта, если у модели
другой чат-темплейт). `cleanupStaleModels()` при этом сам удалит старый `.gguf`, чтобы сотни
мегабайт не висели мёртвым грузом.

Сверенные кандидаты (размеры проверены через HF API):

| Модель | Файл | Байт |
|---|---|---|
| Qwen2.5-0.5B-Instruct Q4_K_M (**текущая**) | `qwen2.5-0.5b-instruct-q4_k_m.gguf` | 491 400 032 |
| Qwen2.5-1.5B-Instruct Q4_K_M | `qwen2.5-1.5b-instruct-q4_k_m.gguf` | 1 117 320 736 |

### 2.4 Скачивание модели никогда не должно идти внутри `infer()`

**Симптом (исторический).** Закачка запускалась внутри `infer()`, т.е. на единственном
сериализованном dispatcher'е пайплайна (ADR-005): блокировала его на ~48 с, падала с
`SocketException` на большом файле и начинала заново с нуля на каждое SMS — не завершаясь никогда.

**Фикс.** `infer()` **никогда** не качает: нет модели → возвращает `null` (regex-only) и
запускает фоновую докачку. Сама докачка — отдельный поток, с докачкой по **HTTP Range**
(частичный файл в `.part` переживает обрывы), ретраями и переименованием в финальный файл
только после проверки размера. Поэтому `infer()` никогда не увидит недокачанный файл.

## 3. Regex / Atomizer

### 3.1 Unicode-регексы: desktop-JVM ≠ Android

**Симптом.** На устройстве — `NoClassDefFoundError: RegexAtomizerKt`, хотя класс есть в dex.

**Причина.** Это не отсутствие класса, а **падение статического инициализатора** (`<clinit>`)
при компиляции паттернов. Конкретно:
- на JVM `\w`/`\s`/`\b` по умолчанию матчат только ASCII, а `(?i)` без `U` не даёт
  регистронезависимости кириллице/казахскому (в отличие от Python, где для str-паттернов
  Unicode включён неявно) — без флагов паттерны на кириллице **молча** переставали матчиться;
- инлайновый префикс `(?iU)` работает на desktop-JVM, но **Android его отвергает**;
- флаг `UNICODE_CHARACTER_CLASS` на Android **вообще не поддерживается** —
  `IllegalArgumentException: "UNICODE_CHARACTER_CLASS flag not supported"`.

**Фикс.** Все RU/KZ-паттерны компилируются через хелпер `ruKz(pattern)`, который:
заменяет `\w` → `[\p{L}\p{N}_]` вручную (свойства `\p{...}` Android поддерживает) и
ставит флаги `CASE_INSENSITIVE | UNICODE_CASE`. `\s`/`\d`/`\b` остаются ASCII — для наших
паттернов этого достаточно.

> **Если новый RU/KZ regex добавлен в обход `ruKz` — это баг.**

### 3.2 Двухтировый OTP: recall против precision

**История в две итерации** — полезна как иллюстрация компромисса из ADR-007.

1. *Мало recall.* Ловились только «продиктуйте код»/«назовите код». Реальное «код скажи…»
   давало `category=none` → **и LLM не вызывался** (гейт `category != none`) → скам пропускался.
2. *Слишком много.* После расширения на «глагол + код» стало ловиться обычное «дай код»,
   «код сообщения» — ложные тревоги в дев-переписке. **LLM это погасить не может**: политика
   Aggregator `max()` (ADR-005) только повышает уровень, никогда не понижает — значит
   precision обязан жить в самом регексе.

**Итоговое решение — два тира:**
- **STRONG** (однозначные, срабатывают сами): `код подтверждения`, `смс-код`,
  `продиктуйте/назовите код`, `никому не сообщайте`.
- **WEAK** (`глагол + код`: скажи/дай/сообщи/передай/отправь/напиши) — срабатывают **только
  при скам-контексте рядом** (`OTP_CONTEXT`: смс/банк/каспи/halyk/доставка/заблокир/срочно/
  счёт/карта/whatsapp…).

Итог: «скажи код» само по себе — тишина, «код скажи, доставка каспи» — тревога.

**Обобщённый механизм.** В `Rule` есть два поля корроборации, `atomize()` проверяет оба:
- `requiresUrl` — правило считается только при наличии URL (это `phishing_link`: тревожная
  фраза без реальной ссылки — обрывок, не скам);
- `contextAny` — правило считается только если в тексте есть ещё и этот контекст (слабый OTP).

> Добавляя новый неоднозначный паттерн — вешай на него `contextAny`, а не расширяй сильный тир.

### 3.3 Импперсонация банка: пустой отправитель ≠ скрытый номер

**Симптом.** Ложный `DANGER` на легитимных банковских уведомлениях.

**Причина.** В проверку импперсонации-по-номеру передавался `EXTRA_TITLE` уведомления — а это
**отображаемое имя** (для банк-приложений почти всегда буквенное, «Kaspi.kz»), не номер.
Ветка «номер буквенный/скрытый → банки так не звонят» срабатывала на любом упоминании банка.

**Фикс (два уровня).**
- `impersonationFlag()` возвращает `null` при пустом отправителе: **нет номера ≠ импперсонация**.
- В NLS заголовок передаётся в проверку, только если он действительно похож на телефонный
  номер (`looksLikePhoneNumber`: достаточно цифр и нет букв).

Текстовый сигнал `bank_impersonation` при этом продолжает корректно работать через `RegexAtomizer`.

## 4. Android-платформа

### 4.1 Петля обратной связи NLS

**Симптом.** Бесконечный цикл алертов.

**Причина.** Собственное heads-up уведомление щита («Осторожно…» с текстом «Никому не
называйте код…») читалось нашим же `NotificationListenerService`, матчило OTP-паттерн и
порождало новый алерт.

**Фикс.** `if (sbn.packageName == packageName) return` в начале `onNotificationPosted`.

> Общее правило: **любой listener, который сам порождает события своего же типа, обязан
> отфильтровать себя первым делом.**

### 4.2 NLS перепубликует одни и те же уведомления

**Симптом.** По логу — одно и то же сообщение прогонялось через пайплайн **8+ раз в минуту**;
для скам-уведомления каждый повтор означал новый ~секундный LLM-инференс.

**Причина.** `onNotificationPosted` срабатывает на любое **обновление/переранжирование**
уведомления, а не только на новое.

**Фикс (оба — ДО `scope.launch`, чтобы мусор не попадал на dispatcher):**
- `shouldSkip()` — отсев постоянных/системных: флаги `FLAG_ONGOING_EVENT`,
  `FLAG_FOREGROUND_SERVICE`, `FLAG_GROUP_SUMMARY` + категории `PROGRESS/SERVICE/TRANSPORT/
  SYSTEM/STATUS/ALARM/NAVIGATION/STOPWATCH` (заряд батареи, медиаплеер, сводки чатов скамом не бывают);
- `isDuplicate()` — дедуп по `sbn.key` + `hashCode(text)`.

**Порядок проверок в `onNotificationPosted`:** свой пакет → ветка звонка → `shouldSkip` →
`extractText` → `isDuplicate` → пайплайн.

### 4.3 Звонки мессенджеров не видны `CallScreeningService`

**Ограничение платформы.** `CallScreeningService` + `ROLE_CALL_SCREENING` (ADR-011) видит
**только** звонки через системный Telecom-стек, т.е. сотовые. Звонки WhatsApp / Telegram /
Viber / Signal / Skype / Google Meet — это VoIP (self-managed `ConnectionService`), и
`onScreenCall()` для них **не вызывается**. А для целевой аудитории это сегодня один из
основных векторов.

**Обходной путь (реализован в NLS).** Уведомление-звонок мессенджера распознаётся по
`packageName ∈ VOIP_CALL_PACKAGES` **и** (`category == CATEGORY_CALL` **или** наличие
full-screen intent) — и армит то же «окно рискованного звонка» через `ShieldEngine.onCallStarted`.
Дальше вся корреляция действий (OTP-SMS / remote-access / банк-апп во время звонка) работает
как для сотовых.

Тонкость с определением звонящего: мессенджер показывает **имя**, если номер в контактах, и
**номер**, если нет. Поэтому: заголовок-имя → окно **не** армим (иначе ложный DANGER на
легальном звонке родни); заголовок-номер → незнакомый звонящий → армим.

**Честные ограничения.** Аудио звонка недоступно (как и у сотовых); номер известен только
если звонящего нет в контактах; это эвристика по уведомлению, а не системный контракт.

### 4.4 У `CallScreeningService` нет колбэка окончания звонка

**Симптом.** После первого же звонка с незнакомого номера окно «рискованного звонка»
оставалось открытым **навсегда**, и любая последующая OTP-SMS трактовалась как DANGER.

**Причина.** `ShieldEngine.onCallEnded()` не вызывался ниоткуда: `CallScreeningService`
уведомляет только о **начале** скрининга.

**Фикс — два уровня (страховка + точность):**
1. **Таймаут окна** `ShieldEngine.RISKY_WINDOW_MS` (10 мин) — окно самозакрывается в
   `duringRiskyCall()`. Работает всегда, без разрешений.
2. **Точный конец звонка**: `app/pipeline/CallStateWatcher` слушает `TelephonyCallback`
   (API 31+) / `PhoneStateListener` и на `CALL_STATE_IDLE` зовёт `onCallEnded()`.
   Требует `READ_PHONE_STATE`; без разрешения — graceful degradation на таймаут.

Для **мессенджер-звонков** точный сигнал конца есть и без телефонии: `onNotificationRemoved`
для того же `sbn.key`, которым армили окно.

### 4.5 Гонка данных за `CallState`

**Симптом.** Потенциально несогласованное состояние окна звонка (проявляется редко — нужно
совпадение звонка и SMS).

**Причина.** `ShieldPlanner.engine` — синглтон, но трогается из **трёх** потоков:
`onSms` — с dispatcher'а пайплайна, `onCallStarted` — с Binder-потока `CallScreeningService`,
`onAppInstalled` — с main-потока `BroadcastReceiver`. Сериализован был только первый.

**Важно про инвариант.** Однопоточный `ShieldPlanner.dispatcher` сериализует **доступ к
`llama_context`** (требование ADR-005), но **не** доступ к `CallState` — события звонков и
пакетов идут мимо него.

**Фикс.** Все публичные методы `ShieldEngine` помечены `@Synchronized`.

### 4.6 Почему shortService FGS не подключён к пайплайну

**Решение (не баг).** `ShieldPipelineForegroundService` (ADR-008) остаётся скелетом и
**не используется** для прогона пайплайна. Причины:
- инференс укладывается в секунды, а NLS-колбэк держит процесс на perceptible-важности —
  отстрел не угрожает;
- per-message FGS дал бы **видимое уведомление на каждую проверку**;
- старт FGS из фонового NLS-колбэка на Android 12+ рискует
  `ForegroundServiceStartNotAllowedException` — т.е. можно **сломать рабочий путь** ради
  околонулевой выгоды.

**Триггер пересмотра:** переход на модель 1.5B+ (длинный инференс) или логи, показывающие
отстрелы процесса.

### 4.7 Нет события «пользователь открыл приложение»

В Android нет колбэка на открытие чужого приложения. Поэтому `BankAppMonitor`, пока открыто
окно рискованного звонка, **опрашивает** передний план через `UsageStatsManager.queryEvents`
(интервал ~1.2 с). Разрешение `PACKAGE_USAGE_STATS` уже объявлено, новых не требуется.
Ограничение: без foreground-сервиса опрос живёт, пока жив процесс.

## 5. Сборка и окружение

### 5.1 Чистый пересбор нативки обязателен

После правки `CMakeLists.txt` или флагов компиляции **инкрементальная сборка обманывает**:
ninja переиспользует старые объектные файлы, APK собирается с прежним размером и прежним
поведением. Именно так выглядел симптом «собираю с `-O3`, а ничего не меняется».

**Как делать чисто:** Android Studio → *Build → Refresh Linked C++ Projects* → *Clean Project*
→ *Rebuild Project*; либо удалить `app/.cxx` и `app/build` перед сборкой.

**Как убедиться, что на устройстве новая нативка:** в `llama_bridge.cpp` есть
`NATIVE_BUILD_TAG`, он печатается в лог при `nativeSetLogPath`/`nativeLoad`. Аналогично
Kotlin-сторона печатает `FileLog.BUILD_TAG` при старте. **Бампать оба при значимых правках** —
это дешевле, чем гадать, тот ли APK стоит на телефоне.

### 5.2 Gradle не стартует в терминале ИИ-агента (loopback) + рабочий обход

**Симптом.** `./gradlew` падает с `java.io.IOException: Unable to establish loopback connection`.

**Причина.** В процессном дереве терминала агента **JVM-wide не работает `Selector.open()`**
(проверено голым тестом на 5 строк: `Selector.open()` падает, при этом обычный
`ServerSocket.bind(127.0.0.1)` работает). Gradle без селектора не стартует.
**Это не VPN, не антивирус и не песочница** — отключение VPN и запуск без песочницы не помогают.
Сборка через саму Android Studio при этом работает нормально.

**Обход для `:core`** (проверено): компилировать напрямую компилятором Kotlin из gradle-кеша —
`K2JVMCompiler` селектор не нужен.

```bash
java -cp "<kotlin-compiler-embeddable-1.9.24.jar>;<kotlin-stdlib-1.9.24.jar>;\
<kotlin-script-runtime.jar>;<kotlin-reflect.jar>;<trove4j.jar>;<annotations-13.0.jar>" \
  org.jetbrains.kotlin.cli.jvm.K2JVMCompiler \
  -no-stdlib -no-reflect -cp "<stdlib>;<annotations>" -jvm-target 17 -d <out> <все .kt>
```
Джарники лежат в `~/.gradle/caches/modules-2/files-2.1`. Три обязательных условия:
1. **stdlib ровно той же версии, что компилятор** (1.9.24) — иначе краш IR-backend на inline-функциях;
2. **`annotations-13.0.jar` обязателен** в classpath компилятора, иначе codegen лямбд/
   function-reference падает с `ClassNotFoundException: org.jetbrains.annotations.NotNull`;
3. не делать один гигантский `main()` — упрётся в лимит размера метода JVM (64 КБ).

`:app` так собрать **нельзя** (нужны AGP, ресурсы/`R`, AndroidX).

### 5.3 Диагностика без компьютера — и её предел

`app/log/FileLog.kt` дублирует Logcat в файл
`getExternalFilesDir/logs/shield.log` — читается прямо в приложении (экран лога), потому что
на Android 11+ системные «Файлы» прячут `Android/data`. Плюс глобальный
`Thread.setDefaultUncaughtExceptionHandler` логирует необработанные Kotlin-исключения перед крашем.
Нативная сторона пишет «хлебные крошки» в **тот же файл** (`nativeSetLogPath`, `flog()` с
`fflush`+`fclose` на каждую строку — чтобы последняя строка пережила segfault).

**Предел.** Нативный краш (SIGSEGV) убивает процесс мгновенно — Kotlin-сторона ничего дописать
не успевает. Для таких случаев всё равно нужен `adb logcat`/tombstone с компьютера.
Нативные крошки частично закрывают этот пробел — по последней строке видно, **где** упало.

Метки, по которым в логе видно, что именно установлено на устройстве.

| Метка | Что принесла |
|---|---|

| `2026-07-22-O3+no-double-accept` / `native-2026-07-22-a-*` | Реальный `-O3` для ggml; убран двойной `accept` (SIGSEGV) |

| `2026-07-22-dedup+skip-ongoing` | Дедуп и отсев системных уведомлений в NLS |
| `2026-07-22-qwen2.5-0.5b+fewshot` | Qwen2.5-0.5B, ChatML-промпт, докачка по `Content-Length` |
| `2026-07-22-ctx1024+trim-prompt` | `N_CTX=1024`, подрезанный промпт, `MAX_INPUT_CHARS=1200` |

**Хронология разблокировки LLM** (полезна как карта: каждый следующий баг был не виден,
пока не починен предыдущий):

```
GBNF не парсился  →  segfault на 1-м токене
      ↓ (валидная грамматика + null-check)
нативка на -O0    →  llama_decode 113 с, процесс убивало
      ↓ (add_compile_options(-O3) + чистый пересбор)
двойной accept    →  segfault сразу после 1-го токена
      ↓ (убран лишний llama_sampler_accept)
KV не чистился    →  2-й и 3-й инференс падали на decode
      ↓ (llama_memory_clear + llama_sampler_reset)
ws* в грамматике  →  64 пробела вместо JSON
      ↓ (компактный GBNF без ws)
сырой промпт      →  константный {"level":"none"} на любом входе
      ↓ (ChatML + few-shot)
✅ осмысленные вердикты, привязанные к содержанию
```
